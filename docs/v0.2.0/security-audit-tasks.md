# Security Audit Tasks

1. ✅ Review and reconsider architecture for `data-hf-sync/models_queue.json` ~ `https://huggingface.co/buckets/mflux-community/ci/resolve/models_queue.json?download=true`. Decided: DO Spaces (`app/queue_store.py`) is the real master; the HF bucket copy is a throwaway mirror, refreshed via `push("models_queue")`.
2. **Verified 2026-08-20, resolved.** `app/queue_store.py`'s queue master moved off DO Spaces onto `cleverheart2026/mflux-model-gpu-runner-storage` (the GPU worker Space's own companion bucket, `queue/` prefix) -- checked directly with real `HF_TOKEN` access: the bucket is **private** (`bucket_info(...).private == True`) and owned by the `cleverheart2026` personal account, not a shared org bucket. That's a simpler model than the original DO Spaces question assumed (which was really about a multi-admin shared-org boundary) -- access here is just "whoever holds this one personal HF_TOKEN," and that token is already confirmed live to have write access (queue/, results/, and build/ prefixes were all written successfully this session).
3. **Reviewed 2026-08-20, currently clean, but not a one-time close-out.** `data-hf-sync/models_queue.json` now has real (non-placeholder) data -- 2 entries, both with `"note": null`. Everything else in an entry (`model_stem`, `quants`, `force_hf_overwrite`, `status`, `added_at`) is public model-build metadata, no secrets/PII. The risk surface is `note` (`app/main.py`'s `QueueEntryRequest`/`QueueEntryUpdateRequest`, a freeform `str | None` a human can type anything into) -- clean today only because nobody's used it for anything sensitive yet. Re-scan whenever real `note` content shows up, not just once.
4. **Still open, blocked on 3.** No action needed right now (3's current answer is clean), but the actual policy decision -- sanitize/remove the HF mirror before any wider release, or accept `note` as a standing PII/secrets risk and rely on re-scanning -- hasn't been made.
5. **Confirmed live 2026-08-21, open.** `POST /generate` with `dispatch=true` silently orphans a `runs` row when the HF Spaces worker is unreachable. `generate_one` (`app/generate.py:227-236`) writes the `runs` row (default status `running`) *before* calling `trigger_fn`; when `trigger_fn=dispatch_trigger` hits `httpx.HTTPError` (worker offline/unreachable) it raises `DispatchConfigError`, which propagates straight through `generate_one` and out of the `/generate` handler as a 503 (`app/main.py:504`) -- nothing catches it to mark the run row `failed`. No jobs are actually queued on the worker, but the run sits at status `running` forever with no retry. Reproduced live: dispatching Fibo-lite q5/q3 while the worker was down left run #28 stuck as "running" after the client got a 503. Fix would be to wrap the `trigger_fn(...)` call in `generate_one` so a `DispatchConfigError` (or any trigger_fn exception) finishes the run as `failed` instead of leaving the default status in place -- not yet implemented.
